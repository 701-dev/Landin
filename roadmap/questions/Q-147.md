# Q-147 — How should the I/O concepts be grouped?

Asked by R20.10 on 2026-11-22.

The inventory's fifth question. D268 keeps the I/O concepts narrow so a
firmware provider supplies only what it has. Two consequences are
awkward: `io.world` has no entries of its own (`world is reader, writer,
files, process`), and `any world` does not convert to `any writer`, so
the library carries `lent`, `lent_writer` and `writer_of`. Finding 2 also
names pairs that say one idea twice: `io.writer.write` and
`text.outlet.take`, and the file operations split over `files`,
`file_system` and `directories`.

**Options:**

1. Keep them narrow, and fix `world` so that `any world` gives each part
   without `lent` (by Q-144's parent conversion if taken, or by entries
   that hand out each part); merge a pair only where R20.30 finds the two
   receivers and failures can be one.
2. Keep them narrow and merge the named pairs now: `outlet` into
   `writer`, the three file concepts into as few as a firmware provider
   still splits.
3. One broad `world` with every entry, firmware providers refusing what
   they lack at run time.

**Recommendation:** option 1. D268's reason stands, and the `world` fix
removes the bridge types; merges need the receiver-by-receiver reading
R20.30 does.

**Default until answered:** the inventory's: narrow concepts, `world`
fixed so `any world` gives each part without `lent`.

**What waits on the answer:** R20.30's I/O entries.
