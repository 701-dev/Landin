# Q-336 — Is the M7 lane `core/regex`'s Cortex-M evidence, or should an ARMv6-M lane with room for it be added?

Asked by R22.60 on 2026-11-26.

R22.60's exit evidence asks for linear time pinned on Cortex-M0. A
program that compiles a pattern with `regex.lean()` options and searches
it links about 150 KB of Thumb code at `size/auto`, the parser, the
compiler and the four engines, a third of it generic `core/mem` and
`core/vec` instances (SR-1968); the corpus's ARMv6-M reference profile is
32 KiB of flash and 12 KiB of RAM. The corpus records
`runtime/regex-linear-time` and `runtime/library-shared-regex` there as
`selected-image` limits with their sizes, as it does the `complex-*`
fixtures, and the M7 corpus lane, the `cortex-m0` target at `armv7e-m` on
the AN500's 4 MiB map, executes both. The reference lane's QEMU machine,
the micro:bit, has 256 KiB of flash, of which the profile links 32 KiB
(spec [1990]). Which evidence counts is the shape of the firmware claim,
and so yours.

**Options:**

1. The M7 lane's execution is the Cortex-M evidence, and the 32 KiB
   ARMv6-M profile records the size limit; a smaller `core/regex` for
   ARMv6-M waits for SR-1968.
2. Add an ARMv6-M corpus lane on the micro:bit's full 256 KiB of flash,
   for the fixtures whose rows name it, so that the ARMv6-M code itself
   runs; an environment item of its own.
3. Cut `core/regex` to fit 32 KiB on ARMv6-M, a Pike VM alone with a
   smaller parser chosen through the options as `lean` chooses the
   tables, as part of R22.80.

**Recommendation:** option 1 now, with option 2 as a successor if a
firmware user needs regular expressions on an ARMv6-M part: every real
ARMv6-M part that would run them, the RP2040 among them, has far more
than 32 KiB of flash.

**Default until answered:** the M7 lane's execution is the Cortex-M
evidence, and the 32 KiB ARMv6-M profile records `core/regex`'s size as
a limit.

**What waits on the answer:** nothing in R22.60, which closes on the
default; option 2 or 3 would be an item of its own.
