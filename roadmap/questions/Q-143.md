# Q-143 — When does a library routine take `type is C`, and when `any C`?

Asked by R20.10 on 2026-11-22.

The library inventory's first question, the rule at the bottom of most of
its third finding. The same kind of capability arrives in different
shapes: an allocator is a generic `provider: type is mem.allocator` in 44
routines and `any mem.allocator` in the text builder, which stores it; a
byte sink comes in four shapes and entropy in three; the examples erase
with `any` what the library keeps generic (`any io.world` 30 times). An
erased value provides its concept, so a caller holding `any C` can still
call a generic routine; the rule decides only what the library writes.
It is a library convention, so it is yours.

**Options:**

1. Generic (`type is C`) by default; `any C` only where a value stores the
   provider beyond the call, as the text builder and a fibre group do.
   Written into `core/README.md`'s conventions, every departure on the
   breaking list.
2. `any C` by default for capabilities, generic only where a measured hot
   path needs the specialised call: one shape everywhere, smaller images
   with many providers, a table call on every use.
3. Generic everywhere, a storing type made generic over its provider too.

**Recommendation:** option 1. It is what 44 routines already do, keeps
firmware calls direct, and leaves `any` where erasure is forced.

**Default until answered:** the inventory's: generic in `core`, `any` only
where a value stores the provider, written into `core/README.md`.

**What waits on the answer:** R20.20's convention and the receiving
entries of the breaking list.
