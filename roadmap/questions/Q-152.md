# Q-152 — Do the library's containers iterate through `iterable`, and who declares it (SC-17, SR-1284)?

Asked by R20.10 on 2026-11-22.

R19 left SC-17 here: remove the protocol only if containers do not
iterate. The compiler recognises `iterable` by name for `for x in s`, but
no library module declares it and the tour does not say a program must
(SR-1284); no library type conforms, and containers hand out slices
(`for value in vec.used(numbers)`). Since D1652 removed `try for`,
nothing recognises `fallible_iterable`, which the tour still shows.

**Options:**

1. The library declares `iterable` in a `core` module, the compiler takes
   that declaration, and the containers whose items are not one slice
   (`core/map`, `core/tree`) conform; the tour points to it and drops
   `fallible_iterable`.
2. The protocol stays a program's own: the tour says a program declares
   `iterable` itself, containers keep handing out slices, and
   `fallible_iterable` leaves the tour.
3. Remove the protocol (SC-17): `for` walks slices and ranges only, and a
   container is walked with a `while` over its cursor routines.

**Recommendation:** option 1. A concept the compiler knows by name should
have one declaration a reader can find, and `for` over a map is what a
newcomer expects.

**Default until answered:** the protocol stays as it is, the tour
unchanged and SR-1284 scheduled on R20.30.

**What waits on the answer:** R20.30's iteration entry and SR-1284.

**Answer (2026-11-22, the maintainer):** option 1. Recorded as D1957.
