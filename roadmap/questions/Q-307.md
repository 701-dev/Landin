# Q-307 — Does R22.10's exhaustive check of the `f32` functions need to run on the firmware targets?

Asked by R22.10 on 2026-11-25.

R22.10's exit evidence asks for every function within its stated error
of MPFR's values, "one-argument `f32` functions exhaustively and the rest
on a random and a hard-case set, on every target". Checking 2^32 inputs
against MPFR takes about an hour of a 32-core host per function, so the
check runs on the host, not in the gate. `core/math` is written with IEEE
arithmetic alone, which every target rounds alike, so a result is the same
bits on every target: the `math-*` fixtures check each target's results
against MPFR's on their tables in the gate, Cortex-M0, RV32 and Xtensa
included, and the 2^32 results of each function compared bit for bit
against the checked host's carry the exhaustive check to another target.
That comparison is cheap natively and under QEMU's user mode, which runs
Linux arm64 and RV64 programs; a firmware target under QEMU's system
emulation would take days per function.

**Options:**

1. Exhaustive against MPFR on Linux x86-64, the same 2^32 results compared
   bit for bit on Linux arm64 and RV64 in a recorded run, and every target
   in the gate on the fixtures' random and hard-case tables.
2. As 1, and the bit-for-bit comparison also on Darwin, FreeBSD and Windows,
   natively, in a recorded run on each.
3. Exhaustive on every target, the firmware ones included.

**Recommendation:** option 1. Identical bits on two other architectures,
one of them RV64 with its own float unit, and the gate's tables on all of
them, show what a third host would show.

**Default until answered:** option 1: the exhaustive check against MPFR on
Linux x86-64, compared bit for bit on Linux arm64 and RV64 under QEMU, and
the tables on every target in the gate.

**What waits on the answer:** nothing in R22.10, which closes with the
default's runs; options 2 and 3 add recorded runs afterwards.

**Answer (2026-11-26, the maintainer):** "we have to exclude this from
regular gates in general, since this time investment is not
sustainable": the exhaustive check runs on no firmware target and in no
regular gate, and neither does any check of its size. Such a check is
run on a host and recorded against the emitted code it checked, and the
gate only says whether the record still covers the tree; R22.35 makes
that the rule, records it as a decision in `spec.md`, and takes
R22.10's runs as its first record. Closed.
