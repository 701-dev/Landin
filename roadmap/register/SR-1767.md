The gate's `windows-microsoft` job links the corpus with whatever Clang and Visual Studio GitHub's `windows-2025` image carries: Clang 20.1.8 and Visual Studio 18 with MSVC 14.52.37025 in R21.50's runs, which `summary.json` records. Nothing pins either, so an image update can change the verdict's tools between two runs of one tree; R21.50 met this as a `link.exe` behaviour, folding the thread-storage template into `.rdata`, that no local host could show. R21.51's `windows-arm64-microsoft` job does the same on `windows-11-arm`, whose image carried Clang 22.1.8 and the same Visual Studio; that Clang's default linker for the MSVC target is `lld-link`, which refine's `-fuse-ld=link` (D2388) now overrides. llvm-mingw's pinned Windows release, which `windows-debugger` fetches, carries a Clang too, but whether it finds Visual Studio's linker and the Windows SDK as the image's Clang does was not tried.

Completion: the job runs a pinned Clang and names the Visual Studio and SDK versions it requires, refusing another, or the register records why the image's tools are the evidence wanted.
