A routine that returns nothing is written `-> none`, and neither refusal a newcomer meets on the way says so. `f: (inout row: [2]u32) =` is L0103, "a signature says what it returns after `->`, not `=`", whose note describes the returns but names no spelling for none; the natural next try, `f: (inout row: [2]u32) -> () =`, is L0100, "a name belongs here", with a cascade of "this function is never closed". Met writing a test program for R19.30; the spelling came from grepping the fixtures.

R20.20 met the same recovery inside a concept: an entry that takes a type of its own, `pull: (self: provider, other: type is drain, s: other) -> none`, is refused with L0010, "`type` requires a type declaration or a generic formal", which is clear, and then with L0104, "this concept is never closed", though the concept's `end` stands on the next line.

Completion: either refusal names `-> none` when the parameter list is followed by `=` or by `()`, and after an unparsable signature the parser resumes at the next entry or declaration, so neither source gives a "never closed" refusal; a negative fixture for each.

Kept: R20.50, the window item that took it past ten items, renamed library names on the breaking list and touched no compiler source; its activation is a compiler change, and R20.60, which adds the renamed names' refusals, is the next item that may meet it. R20.20 added the concept case above.
