Starting a child program needs two things the library does not give. `io.spawn` and `posix.spawn` take no working directory, and nothing changes the process's own (`docs/library.md` says so on purpose), so a child always starts where its parent is; refine-build starts every step as `env -C VIEW PROGRAM`, which needs GNU coreutils' `env` and is not on macOS. And `io.spawn` never searches PATH, rightly, but nothing else does either, and `io.status` has no executable bit, so a tool writes its own search (30 lines in refine-build's `files/files.ldn`) and takes the first regular file. Met writing refine-build (friction entries 6 and 7).

A program cannot learn the name it was run by: `io.argument_at` starts at the first argument after the program's name, C's `argv[1]`, and nothing in `core/io` gives `argv[0]`. A contributed command answering `--describe`, which the dispatcher holds to its file's name `refine-NAME`, has to write its name in, so a copy under another name describes itself wrongly and is refused; nor can a usage line say the name the program was called by. Met writing refine-build (friction entry 17).

Completion: a child's working directory in `io.spawn`'s arguments, through `posix_spawn_file_actions_addchdir` on Darwin and FreeBSD and `chdir` in the cloned child on Linux; a library PATH search with an executable bit in `io.status`; and the program's name, as the host passed it, readable through `core/io`'s process concept, with its fakes giving one.
